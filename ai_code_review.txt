### 1. Correctness

The code's logic is fundamentally correct. I did not find any defects that would produce incorrect calculation results. The core approach?elementwise accumulation in `dot_product`, with `matvec_multiply` reusing `dot_product` for each row?is sound. Two implementation details deserve recognition:

- `_validate_vector` skips the `math.isfinite` check for Python `int` values. Python integers have arbitrary precision, and calling `math.isfinite` on an extremely large integer could raise an unexpected `OverflowError` when converting it to a float. This is a correct and thoughtful design choice.
- `dot_product` explicitly excludes `bool` values through `isinstance(value, bool)`, preventing `True` and `False` from silently participating in arithmetic as `1` and `0`. This commonly overlooked pitfall is handled correctly here.

### 2. Edge Cases

1. **Empty vectors / empty matrices**: `dot_product([], [])` returns `0`, and `matvec_multiply([], [])` returns `[]`. Both match the documentation, and I verified that the logic is correct.
2. **NaN handling (optional improvement, not a defect)**: During input validation, `_validate_vector` already rejects NaN/inf inputs using `math.isfinite`, so NaN should theoretically not enter from outside. However, NaN could still arise during summation from operations such as `inf + (-inf)`. For example, a row containing very large positive and negative values might overflow to infinity and then cancel to NaN. The `not math.isfinite(total)` check around line 33 of `dot_product` would still catch this and raise `OverflowError`, so the outcome is **safe**. However, the error message "dot product exceeded finite numeric range" is not entirely accurate for NaN: NaN is "undefined," rather than "out of range." This is an optional wording improvement that does not affect correctness.
3. **Nonrectangular matrices (an implicit constraint, not a defect)**: The docstring says "rectangular list/tuple of rows," but the code does not explicitly check that all rows have the same length. Instead, it relies on each row matching the length of `vector` inside `dot_product`. Because every row must match the same vector, this indirectly guarantees a rectangular matrix. The logic is consistent, but the docstring could explain that this is "indirectly guaranteed by matching the vector length," rather than through a separate rectangularity check, to avoid implying that dedicated validation exists.

### 3. Exception Handling

1. **Row-level error messages lack specificity (a concern worth addressing)**
   Location: The loop in `matvec_multiply` calls `dot_product(row, vector)`, while `dot_product` uses the fixed strings `'vector_a'` and `'vector_b'` as variable names in error messages; see `_validate_vector(vector_a, 'vector_a')`.
   Issue: If a row in `matrix` has an invalid type or incompatible length, the exception message is "vector_a must be a list or tuple" or similar text. It **does not tell the user which matrix row caused the error**. Locating the problematic row in a large matrix, such as a 1000?1000 matrix, can be difficult.
   Suggestion: `matvec_multiply` could catch exceptions from `dot_product` and re-raise them with a row index, for example `raise ValueError(f'row {i}: {e}') from e`. Alternatively, `dot_product` could accept an optional name parameter to customize error messages. This is a real usability defect, not merely a nice-to-have enhancement.
2. **Appropriate exception types**: `TypeError` handles invalid types, `ValueError` handles length mismatches and nonfinite values, and `OverflowError` handles overflow during arithmetic. Their roles are clear and consistent with Python conventions.
3. **Unhandled input patterns**: If `vector` is valid but `matrix` contains `None` or a noniterable object as a "row," `dot_product` first checks `isinstance(vector_a, (list, tuple))` and raises `TypeError`. This path is covered and presents no problem.
